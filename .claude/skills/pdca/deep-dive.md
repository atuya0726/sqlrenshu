# 調査の手順

月曜の「調査の回」で使う。結果は `docs/research.md` に書く。

```sh
S=~/.claude/skills/search-console/gsc.py
G="python3 $S --key gsc-sqlrenshu"
SITE=sc-domain:sqlrenshu.com
```

## 1. 施策の検証

`docs/operations.md` の「施策の検証」の表で、評価日が今日以前で、結果が空のものを評価する。

1. 対象ページの数字を、実施前の28日と直近の28日で取る。

   ```sh
   $G query $SITE --by query --page-contains /sql/case/ --start 2026-10-16 --end 2026-11-12
   $G query $SITE --by query --page-contains /sql/case/
   ```

2. 表示回数、平均順位、クリックと、狙った検索語の順位を比べる。
3. 結果を表に書く。数字と、次の3つのどれかを付ける。
   - **効いた**: 同じ型の施策を、ほかのページへ広げる候補として「検索語の機会」に足す。
   - **効かなかった**: 理由の仮説を1つ書く（インデックスされていない、競合が強い、検索意図とずれている、など）。確かめる方法があれば確かめる。
   - **判断できない**: 表示回数が少なすぎるとき。評価日を28日延ばす。2回延ばしても判断できなければ、需要が無かったと見なす。

サイト全体の数字が動いた時期は、その影響を差し引いて読む（例: 11/13 の新版への入れ替え）。

## 2. 検索語の深掘り

### 2.1 全件を取る

```sh
$G query $SITE --by query,page --days 90 --limit 5000   # 検索語とページの組
$G query $SITE --by page --limit 1000                    # ページ別（直近28日）
$G query $SITE --by query,page --days 28 --limit 5000    # 直近28日
$G query $SITE --by query,page --start <56日前> --end <29日前> --limit 5000   # その前の28日
```

直近28日とその前の28日を比べ、新しく出た検索語、順位が3以上動いた検索語を拾う。

### 2.2 ページごとに分ける

検索語をページごとにまとめ、次のどれに当たるかを決める。

| 型 | 見分け方 | 打ち手 |
|---|---|---|
| 伸ばせる | 順位4〜15で、表示がある | 検索語の語が見出しや本文にあるかを確かめ、無い論点を足す。競合調査の第一候補 |
| 意図に合っていない | 順位20より下なのに、表示がある | 上位のページと論点を比べる。浅いのか、別の意図のページなのかを見分ける |
| 受け皿が無い | 検索語に合うページが無く、近いページが出ている | 専用のガイドか、セクションを作る |
| 派生の検索語 | 「case null」「case where」のように、主題＋語の形 | その語を見出しにしたセクションがあるかを確かめる。無ければ足す |
| 別の製品の意図 | 「oracle」「sql server」「mysql」を含む | PostgreSQL との違いを1節で書く価値があるかを、表示回数で決める |
| 順位は高いのにクリックが無い | 順位5位以内、表示20以上、CTR が低い | title と description を検索語に合わせる（28日に1回まで） |

確かめるときは、ページの実物を読む。見出しは `src/data/` のガイドの定義か、本番の HTML で見る。「たぶん書いてある」で済ませない。

### 2.3 Search Console に出ない需要を補う

サイトが小さいうちは、Search Console の行が少ない（2026-11 時点で90日に約50行）。自分のサイトに来ていない検索語は、ここからは見えない。次で補う。

- **サジェスト**: `python3 scripts/suggest.py "sql case文" "sql 結合"` で、Google のサジェストを取る。主題に続く語（「複数条件」「null」「where句」など）は、求められている論点の一覧として使える。検索の量までは分からない。
- **関連する検索**: WebSearch で主題を検索し、結果に並ぶ題名から、よく扱われている論点を拾う。
- **Bing**: Web Analytics の流入元で Bing が多い。Bing の検索語は取れないので、流入のあるページを Web Analytics のページ別で見て、どのテーマが読まれているかを確かめる。

### 2.4 テーマを選ぶ

候補を `docs/research.md` の「検索語の機会」に書き、次の3つで並べる。

- **需要**: 表示回数。無ければ、サジェストの数と、競合がそのテーマにページを持っているか。
- **勝てる見込み**: 今の順位、上位のページの質（古い、浅い、実行できない、広告だらけなら見込みがある）。
- **手持ち**: すでに問題やガイドがあり、少ない加筆で済むか。

上から1〜2個を、次の競合調査にかける。毎週同じテーマを選ばない。前回調べたテーマは、仕様を実装して評価日が来るまで触らない。

## 3. 競合調査

選んだテーマ1つにつき、次を行う。ページの読み取りは Sonnet のサブエージェントに任せ、表の形で返させる。

### 3.1 上位のページを集める

対象の検索語2〜3個を WebSearch で検索し、上位に出るページを5〜8本集める。日本語のページを優先する。WebSearch の順位は Google の日本での順位と同じではないので、順位そのものは根拠にしない。公式ドキュメント、Q&A サイト、動画は、比べる相手から外す（何が出ているかは記録する）。

### 3.2 読んで表にする

各ページを WebFetch で取得し、次を記録する。

- URL、サイト名、更新日（分かれば）
- 見出しの構成（h2 と h3）
- 扱っている論点（例: 単純 CASE、検索 CASE、ELSE を省いたとき、NULL の扱い、WHERE や ORDER BY の中での使い方、集計との組み合わせ）
- 例の質（表と結果が載っているか、実行できるか）
- 練習問題があるか
- 対象の製品（PostgreSQL、MySQL、Oracle、SQL Server、指定なし）
- 弱いところ（古い、誤り、例が動かない、説明が飛ぶ）

取得できなかったページは、できなかったと書く。題名から中身を推測しない。

### 3.3 自分のページと並べる

自分のページも同じ項目で記録し、論点ごとに「相手の何本が扱っているか」「自分は扱っているか」を表にする。

- 相手の半分以上が扱っていて自分に無い論点 → 足す。
- 相手の1〜2本だけが扱っている論点 → サジェストか検索語に出ていれば足す。
- 自分にしか無いもの（その場で実行、練習問題、PostgreSQL での正確さ） → 冒頭や見出しで見えるようにする。
- 相手の弱いところ → そこを確実に上回る内容を書く。

### 3.4 月の最初の月曜: サイト全体の差

月に1回、常連の競合サイト2〜3個の目次か sitemap を見て、相手にあって自分に無いテーマを列挙する。`docs/research.md` の「競合」の表を更新し、無いテーマは「検索語の機会」に足す。

## 4. 仕様づくり

`docs/research.md` の「仕様」に、次の形で書く。木曜の自分が、調べ直さずに書き始められる細かさにする。下は書き方の例で、根拠の数字は実際の調査結果ではない。

```markdown
### /sql/case/ に「NULL の扱い」「WHERE の中で使う」を足す

- 優先度: 高
- 種類: 既存ページの加筆
- 対象の検索語: sql case文（表示16、順位11.1）、sql case null（表示3、順位22）、sql where case（表示1、順位7）
- 根拠: 上位6本のうち5本が NULL の扱いを、4本が WHERE での使い方を扱う。自分のページには無い。サジェストに「null」「where句」がある
- 足すもの:
  - h2「CASE と NULL」: `CASE col WHEN NULL` が真にならない理由、`IS NULL` で書く形。実行できる例を1つ
  - h2「WHERE と ORDER BY の中で使う」: 例を2つ。対応する問題（case-0X）へのリンク
- 確かめること: 単純 CASE と NULL の比較の挙動を、PostgreSQL 公式ドキュメントの条件式の章で確かめる
- 評価: 実施の28日後に、/sql/case/ の表示回数と「sql case文」の順位を見る
```

仕様は常に2件以上を保つ。5件を超えたら、優先度の低いものを「検索語の機会」に戻す。
