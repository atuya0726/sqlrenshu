# 定期の運用（PDCA）

目標は月1万円の収益で、当面はPVを増やす。PVは、検索する人が求めている内容をページが持っていて初めて増える。だからこの運用の中心は、数字の記録や点検ではなく、**検索する人が何を求めていて、上位のページに何があり、自分のページに何が足りないかを調べ、それを埋めること**である。

数字を表に足して、バックログの先頭を1つ消すだけの回は、失敗と考える。毎週、次の問いに答えを出す。

- 先週までにやった施策は効いたか。効かなかったなら、なぜか。
- 今いちばん伸ばせるテーマはどれか。その根拠になる検索語と数字は何か。
- そのテーマで上位にいるページは何を書いていて、自分のページに無いものは何か。

## 週の流れ

| 回 | 役割 | 時間の使い方 |
|---|---|---|
| 月曜 | **調査の回**: 検証、検索語の深掘り、競合調査、仕様づくり | 調査が8割。実装は、調査で見つかった小さな加筆だけ |
| 木曜 | **実装の回**: 月曜に作った仕様の先頭を実装して本番に出す | 実装が8割。数字は合計を見るだけ |

月曜でも木曜でもない日に起動されたときは、`docs/research.md` の「仕様」に未実装のものがあれば実装の回、無ければ調査の回として動く。

置き場所は3つ。

- `docs/operations.md`: 運用の状態、週次の数字、施策の検証、バックログ、ログ。
- `docs/research.md`: 調査の結果。検索語の機会、競合、テーマごとの差、実装待ちの仕様。
- `deep-dive.md`（このファイルと同じディレクトリ）: 調査の手順。月曜は必ず読む。

## 無人実行のとき

スケジュール実行では、途中で誰も答えない。

- ユーザーに質問しない。判断がつかないことは実行せず、「ユーザーに依頼中」に書いて報告する。
- 元に戻しにくい変更（title と description、URL、ナビゲーション、ページの削除）で迷ったら、やらないほうを選ぶ。本文の加筆や新しいガイドは、根拠があるならためらわない。
- 最後に必ず Discord へ報告する。何も変更しなかった回も、調べて分かったことを送る。

## 1. 始める前の確認

1. `docs/operations.md` と `docs/research.md` を読む。
2. `git status` を見る。未コミットの変更があれば、ユーザーの作業中かもしれないので、触らずに中止して報告する。
3. `git pull --ff-only` で最新にする。
4. 本番の生存確認をする。`https://sqlrenshu.com/` と、ガイド、問題のページを1本ずつ取得し、200 で本文が返ることを見る。落ちていたら、ほかの作業より先に原因を調べて報告する。
5. 壊れているもの（本番の不具合、落ちているテスト）と、「ユーザーに依頼中」でチェックが付いた項目があれば、先に片づける。

## 2. 数字を見る

毎回取るのは合計だけ。ここに時間をかけない。

- Web Analytics: 直近7日の合計と日別（`cloudflare-web-analytics` スキル）。
- Search Console: 直近28日の合計（`search-console` スキル）。

月曜は `docs/operations.md` の「週次の数字」に1行足す。

読むときの注意。

- 1日単位の増減は偶然の範囲。判断は週次の数字と、表示回数、掲載順位の動きで行う。
- Search Console は2〜3日遅れる。Web Analytics は推定値で、運営者自身のアクセスも入る。
- 施策の効果が検索に出るまで2〜4週間かかる。変更した直後の数字で、その変更を評価しない。

## 3A. 調査の回（月曜）

`deep-dive.md` を読み、その手順で次の4つを行う。

1. **施策の検証**: 「施策の検証」の表で評価日が来たものを、実施前後の数字で評価する。
2. **検索語の深掘り**: 検索語とページの組を全件取り、ページごとに「伸ばせる」「意図に合っていない」「受け皿が無い」に分ける。
3. **競合調査**: 2 で選んだテーマ1〜2個について、上位のページを実際に読み、自分のページと並べて差を出す。
4. **仕様づくり**: 何を足すかを見出しの単位まで決めて、`docs/research.md` の「仕様」に書く。

終わりの条件。次の3つがそろっていなければ、調査は終わっていない。

- 「仕様」に、未実装のものが2件以上ある。それぞれに、対象の検索語、根拠の数字、足す見出し、評価日が書いてある。
- 競合のページを最低5本、本文まで読んだ。検索結果の題名だけで判断していない。
- 調べて分かったことを、Discord の報告に3点書ける。

調査で見つかった小さな不足（既存ページへの1セクション、説明の誤り、導線の抜け）は、その回のうちに実装してよい。大きなものは木曜に回す。

## 3B. 実装の回（木曜）

`docs/research.md` の「仕様」から、優先度の高い順に1件を選んで実装する。仕様が1件も無ければ、調査の回として動く。

- 仕様に書いた見出しを、すべて実装する。一部だけ出して完了にしない。時間が足りなければ、仕様を2つに分けて、残りを次回に回す。
- 仕様の根拠が古くなっていないかを確かめる。対象のページがすでに変わっていたら、仕様を直してから書く。
- 1回に出すのは、新しいガイド1本と対応する問題、または既存ページ1〜2本の大きな加筆まで。サイト全体に及ぶ書き換えはしない。
- 実装したら、仕様を「仕様」から消し、「施策の検証」の表に1行足す。評価日は実施の28日後。

## 4. 実装するときの決まり

`AGENTS.md` の「内容を変えるときの決まり」に従う。そのうえで、運用として次を守る。

- **他サイトの文章や例を写さない**: 競合調査で分かるのは「どの論点が求められているか」まで。説明、例、SQL は自分のデータセットで書き、仕様は PostgreSQL 公式ドキュメントで確かめる。
- **このサイトの強みを足す**: 上位のページが説明だけなら、同じ論点に、その場で実行できる例と練習問題を付ける。相手と同じものを作るだけでは順位は上がらない。
- **title と description は頻繁に変えない**: 同じページは28日に1回まで。変えたら、変更前後の文言と日付をログに残す。そうしないと効果を測れない。
- **URL を変えない、ページを消さない**: 必要だと思ったら、実施せずにユーザーへ依頼する。
- **調査や機械的な作業は下位モデルに任せる**: 競合ページの読み取りと要約、検索語の整理は Sonnet、取得やテスト実行は Haiku を目安にする。結果は自分で確かめ、確かめられなかった点はそう書く。
- **AdSense の審査中は構成を大きく変えない**: 「ユーザーに依頼中」に審査待ちの記載がある間は、ナビゲーションや必須ページを動かさない。

## 5. 本番に出す

1. `pnpm test` と `pnpm build` を通す。
2. 落ちたら直す。直せなければ、変更を `git stash` で退避し、デプロイせずに報告する。
3. コミットして `git push origin main`。コミットは施策ごとに分ける。
4. `pnpm deploy`。
5. 本番 URL で、変更が出ていることを確かめる。出ていなければ原因を調べる。

## 6. 記録する

`docs/operations.md` と `docs/research.md` を更新し、コミットしてプッシュする。

- **ログ**: 日付、やったこと、根拠にした数字、次回の一手を3行以内で足す。調査の回は、分かったことを1行で足す。
- **施策の検証**: 実装したものを足す。評価したものには結果を書く。
- **バックログ**: 終わったものを消し、新しく見つけたものを足す。内容の追加は「仕様」に書き、バックログには内容以外（計測、設定、収益化）を置く。
- **現状**: 変わった事実だけ直す。
- **ユーザーに依頼中**: 新しいお願いを足す。何をどこでするのかを、手順が分かる形で書く。

ログが60行を超えたら、30日より前の行を月ごとの要約1行にまとめる。

## 7. 報告する

`discord-notify` スキルで送る。件名は `SQL練習室 運用 M/D`。本文は次の順で、全体を800字以内にする。

1. 分かったこと（調査の回は3点。検証の結果、伸ばせるテーマ、競合との差。数字を付ける）
2. やったこと（本番に出たかどうかを含む）
3. 数字（直近7日のPVと訪問。月曜は前週との差も）
4. お願い（ユーザーの作業が必要なものだけ。無ければ書かない）
5. 次回やること（どの仕様を実装するか）

失敗や中止のときは、何が起きて、今どういう状態かを先頭に書く。

## やらないこと

- 外部サービスへの投稿、登録、申請、課金。
- 秘密の値の表示やコミット。
- 確かめていない数字や実行結果の掲載。
- テストかビルドが落ちた状態でのデプロイ。
- 許可を広げる設定変更（`.claude/settings*.json` の許可リストなど）。
- 根拠の無い思いつきの実施。選んだ理由を、検索語か競合との差で説明できるものだけを行う。
