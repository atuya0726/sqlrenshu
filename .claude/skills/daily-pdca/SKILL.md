# 毎日の運用（PDCA）

目標は月1万円の収益で、当面はPVを増やす。1回の実行で、確認、選定、実装、記録、報告までを終える。

状態はすべて `docs/operations.md` にある。このスキルは手順と判断基準だけを持つ。

## 無人実行のとき

スケジュール実行では、途中で誰も答えない。次を守る。

- ユーザーに質問しない。判断がつかないことは実行せず、「ユーザーに依頼中」に書いて報告する。
- 迷ったら小さいほうの変更を選ぶ。誤った変更が誰にも止められず本番に出るため。
- 最後に必ず Discord へ報告する。何もしなかった日も、その理由を送る。

## 1. 始める前の確認

1. `docs/operations.md` を読む。
2. `git status` を見る。未コミットの変更があれば、ユーザーの作業中かもしれないので、触らずに中止して報告する。
3. `git pull --ff-only` で最新にする。
4. 本番の生存確認をする。`https://sqlrenshu.com/` と、ガイド、問題のページを1本ずつ取得し、200 で本文が返ることを見る。落ちていたら、ほかの作業より先に原因を調べて報告する。

## 2. 数字を見る（Check）

毎回取るもの。

- Web Analytics: 直近7日の合計と日別（`cloudflare-web-analytics` スキル）。
- Search Console: 直近28日の合計（`search-console` スキル）。

月曜日、または前回の記録から7日以上あいた日は、週次の記録もする。

- 上の2つを `docs/operations.md` の「週次の数字」の表に1行足す。
- Search Console のページ別と検索語別（直近28日）を見て、前週との違いを確かめる。
- Web Analytics の流入元別とページ別（直近7日）を見る。

読むときの注意。

- 1日単位の増減は偶然の範囲。判断は週次の数字と、表示回数、掲載順位の動きで行う。
- Search Console は2〜3日遅れる。Web Analytics は推定値で、運営者自身のアクセスも入る。
- 施策の効果が検索に出るまで2〜4週間かかる。変更した直後の数字で、その変更を評価しない。

## 3. やることを選ぶ（Act と Plan）

次の順で、その日に終わる大きさのものを1〜2個選ぶ。

1. **壊れているものの修理**: 本番の不具合、落ちているテスト、リンク切れ。
2. **ユーザーの返事で進められるようになったもの**: 「ユーザーに依頼中」でチェックが付いた項目の続き。
3. **期日が来た再計測**: バックログに「◯月に再計測」と書いた項目。
4. **バックログの先頭**。

バックログが3個を切ったら、数字から候補を足す。

- 表示があり掲載順位が5〜20位の検索語で、対応するセクションがページに無いもの → セクションを足す。
- 検索語は来ているが、専用のガイドが無いテーマ → ガイドを足す。
- PVの多いページから次のページへ進む導線が弱いところ → 内部リンクを足す。
- 表示が多く順位が5位以内なのに CTR が低いページ → title と description を直す。

選んだ理由を、数字とともにログへ書けるものだけを選ぶ。根拠の無い思いつきは実施しない。

## 4. 実装する（Do）

`AGENTS.md` の「内容を変えるときの決まり」に従う。そのうえで、運用として次を守る。

- **1回の変更は小さく**: 1日に触るのは、新しいガイド1本か、既存ページ数本の加筆まで。サイト全体に及ぶ書き換えはしない。
- **title と description は頻繁に変えない**: 同じページは28日に1回まで。変えたら、変更前後の文言と日付をログに残す。そうしないと効果を測れない。
- **URL を変えない、ページを消さない**: 必要だと思ったら、実施せずにユーザーへ依頼する。
- **調査や機械的な作業は下位モデルに任せる**: ユーザーの全体ルールに従う。結果は自分で確かめる。
- **AdSense の審査中は構成を大きく変えない**: 「ユーザーに依頼中」に審査待ちの記載がある間は、ナビゲーションや必須ページを動かさない。

## 5. 本番に出す

1. `pnpm test` と `pnpm build` を通す。
2. 落ちたら直す。直せなければ、変更を `git stash` で退避し、デプロイせずに報告する。
3. コミットして `git push origin main`。コミットは施策ごとに分ける。
4. `pnpm deploy`。
5. 本番 URL で、変更が出ていることを確かめる。出ていなければ原因を調べる。

## 6. 記録する

`docs/operations.md` を更新し、コミットしてプッシュする。

- **ログ**: 日付、やったこと、根拠にした数字、次回の一手を3行以内で足す。
- **バックログ**: 終わったものを消し、新しく見つけたものを足す。
- **現状**: 変わった事実だけ直す。
- **ユーザーに依頼中**: 新しいお願いを足す。何をどこでするのかを、手順が分かる形で書く。

ログが60行を超えたら、30日より前の行を月ごとの要約1行にまとめる。

## 7. 報告する

`discord-notify` スキルで送る。件名は `SQL練習室 運用 M/D`。本文は次の順で、全体を600字以内にする。

1. やったこと（本番に出たかどうかを含む）
2. 数字（直近7日のPVと訪問。週次の記録をした日は前週との差も）
3. お願い（ユーザーの作業が必要なものだけ。無ければ書かない）
4. 次回の予定

失敗や中止のときは、何が起きて、今どういう状態かを先頭に書く。

## やらないこと

- 外部サービスへの投稿、登録、申請、課金。
- 秘密の値の表示やコミット。
- 確かめていない数字や実行結果の掲載。
- テストかビルドが落ちた状態でのデプロイ。
- 許可を広げる設定変更（`.claude/settings*.json` の許可リストなど）。
